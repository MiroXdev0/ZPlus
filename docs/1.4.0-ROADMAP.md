# Z+ 1.4.0 Compiler Architecture Roadmap

This roadmap records architectural limits observed in the 1.3.5 stabilization
pass. It is planning material, not a claim that the work is implemented.

## Current limits

- Compilation remains a mostly sequential pipeline with compiler orchestration
  concentrated in the CLI and shared mutable state in semantic analysis.
- The parser, analyzer, IR builder, interpreter, and native backend have
  distinct source files, but their contracts are not yet expressed as stable,
  independently testable compilation interfaces.
- The native backend targets a constrained x86-64 subset; platform/runtime
  support differs from interpreter support, particularly on Linux.
- ZPBuild invokes the compiler per executable or test target. There is no
  object-file or library-link interface, so imports are recompiled with each
  affected target.
- Runtime ownership and GC roots cross compiler-generated ABI boundaries.
  These boundaries require explicit metadata and parity tests as new runtime
  values are introduced.
- Diagnostics are structured in some paths but are not yet one uniform,
  source-mapped diagnostic contract across all stages.

## Recommended work

1. Define immutable source snapshots, source IDs, spans, diagnostics, and a
   compilation context. Make repeated and concurrent compilations independent.
2. Extract lexer/parser APIs that consume source snapshots and return syntax
   plus diagnostics without mutating global state. Add recovery tests before
   changing grammar behavior.
3. Formalize typed IR verification and pass contracts. Keep interpreter and
   native lowering as separate consumers of verified IR.
4. Describe runtime calls, value ownership, GC root locations, and platform
   requirements in versioned ABI metadata generated from one declaration.
5. Introduce source maps and structured diagnostic serialization for parser,
   semantic, IR, and backend failures.
6. Add reusable compiler-service APIs before considering incremental module
   compilation. Measure dependency discovery and compilation separately.
7. Expand platform abstractions around process, filesystem, dynamic libraries,
   and native code emission; keep unsupported host/backend combinations explicit.

## Optimization opportunities

After profiling, evaluate token allocation and source-span storage, repeated
module loading, IR allocation, specialization caching, and duplicate compiler
startup in multi-target builds. Preserve deterministic output and cache
invalidation correctness; do not optimize by weakening validation.

## Testing and compatibility

Require lexer/parser recovery tests, semantic negative tests, IR verifier
tests, interpreter/native parity fixtures, GC stress tests, ABI metadata tests,
and fresh-install tests on Windows and Linux. Test old project manifests and
module layouts before changing resolution. Preserve existing syntax and CLI
behavior unless a migration is documented. Keep ZPM and ZPBuild versioning
independent from the compiler.

## Proposed order

1. Source/diagnostic contracts and compilation context.
2. Parser recovery and semantic-analysis isolation.
3. Typed IR invariants and pass interfaces.
4. Runtime ABI and ownership metadata.
5. Structured source-mapped diagnostics.
6. Platform abstraction and backend parity.
7. Profile-guided incremental compilation and module artifact caching.

Each stage should land with tests and compatibility review before the next.
